# Local unified memory contract (observed implementation)

This document describes the local Squish implementation only. It is grounded in `core/memory/memory-types.ts`, `core/knowledge/types.ts`, `core/knowledge/mental-models.ts`, `core/memory/memory-write.ts`, `core/knowledge/knowledge-crud.ts`, `db/drizzle/schema-sqlite.ts`, and relevant tests. It does not describe or change Cloud behavior.

## Three distinct layers

1. **Durable evidence — `memories`**. A `RememberInput` is written as a memory row before derived processing. In `rememberMemory`, `content` remains the original input; embedding enrichment is used for embedding only. This path supplies typed content, resolved project/user/team scope, tags and metadata, source, status, sector/tier, timestamps, validity, and encryption state. Other lifecycle/governance fields exist in the local `memories` schema but may remain null or use defaults; schema availability does not mean this write path populates each field. `rememberMemory` also places the optional `reasoning`, `memoryContext`, `examples`, and `exceptions` values into JSON `metadata`; these are not separate memory columns. Session identifiers/start time/tool name are likewise nested in `metadata.sessionMetadata` on this write path (not dedicated `memories` columns in the schema shown).
2. **Derived knowledge — `knowledge`**. This is a separate representation/classification, not a replacement for the evidence row. `KnowledgeKind` is `memory | belief | strategy`; `knowledgeType` carries the subtype. The write path attempts a `knowledge` row of kind `memory` for a project-scoped durable memory and independently extracts beliefs and strategies. Errors in these derivations are caught/logged after the durable memory insert. Beliefs carry fields such as `normalizedKey`, `reason`, `evidenceSummary`, `lastConfirmedAt`, and `sourceCount`; strategies carry `title`, `description`, `steps`, success/failure criteria and usage counters. `knowledge_edges` records typed links to knowledge, entities, or places. The local schema has `knowledge.evidence` and `knowledge.consolidated_from`; `consolidated_from` is declared in `db/drizzle/schema-sqlite.ts` but is not inserted or mapped by the inspected `knowledge-crud.ts` path / `Knowledge` interface. Treat it as schema-only for this CRUD path unless another writer is verified; callers must not assume it is populated or type-accessible.
3. **Derived project-level mental models — `mental_models`**. These are generated summaries, not raw evidence and not `knowledge` rows. The local runtime-created table stores `id`, `project_id`, `title`, `description`, `content`, `source_memory_ids`, `version`, `last_refreshed_at`, `created_at`, and `updated_at`. Refresh selects up to 40 recent active, unencrypted, nonempty project memories by `created_at`, or accepts explicit `{id, content}` inputs; it prompts a generator, caps generated content at 8,000 characters, records unique source IDs, and increments version. Tests verify that refresh stores content and source IDs. The source list is provenance, not a complete immutable snapshot of every input value; changed/deleted source rows are not embedded in the model record.

## Local database boundaries

The local Drizzle schema entry point (`db/schema.ts`) loads `db/drizzle/schema-sqlite.js`; `db/drizzle/schema.ts` re-exports the SQLite schema for the local-only OSS build. Thus the declared local schema inspected here is SQLite/Drizzle.

`mental-models.ts` separately supports two client shapes at runtime: SQLite (`prepare`/`exec`) and PostgreSQL (`query`). Its SQLite table uses `source_memory_ids TEXT` with JSON serialization and integer epoch timestamps; its PostgreSQL table uses `JSONB` for source IDs and `TIMESTAMPTZ` timestamps. This dual-client logic is localized to mental models and does not establish that all local memory/knowledge operations support PostgreSQL: `knowledge-crud.ts` uses the SQLite `$client.prepare` interface, and the inspected write path accesses SQLite directly for some edge/place operations. PostgreSQL compatibility for those paths is therefore not established by these files. This document does not specify Cloud schema or migration behavior.

## Idempotency and provenance guarantees

- Memory creation assigns a fresh `randomUUID()` and inserts a new row; the inspected path has no upsert/idempotency key. Repeating a request can therefore create another durable row. Similarity/duplicate-detection indexes or later consolidation are not equivalent to write idempotency.
- Knowledge creation likewise assigns a fresh UUID and inserts. `knowledge_edges` has a unique constraint over `(from_id, from_kind, to_id, to_kind, edge_type)`, which makes duplicate identical edges conflict-safe at the storage constraint level; it does not make knowledge creation idempotent.
- Belief derivation has a memory-source adapter and belief source tracking; the write path calls `upsertBeliefsForMemory`. This is narrower than a general guarantee that all derived knowledge is exactly-once.
- Mental-model refresh de-duplicates the supplied source IDs in the persisted JSON array and increments `version` on successful refresh. It does not define a stable generation idempotency key, and repeat refreshes can increment the version again.
- Durable evidence is inserted first; belief/strategy/knowledge derivations are best-effort and may fail independently. Mental-model scheduling is fire-and-forget and coalesces/rate-limits scheduling per project in process memory, not a durable job ledger.

## Test evidence inspected

`tests/core/mental-models.test.ts` verifies create/read/update/list/delete, generated refresh content and `sourceMemoryIds`, version increments, and non-blocking scheduling. `tests/core/memory/beliefs-retrieval.test.ts` verifies that a decision memory can produce a belief-kind row in `knowledge`, that memory rows receive sector and bi-temporal values, and that retrieval identifies memory vs belief corpora. These tests support those specific observed behaviors; they do not establish universal idempotency or PostgreSQL support for the full write stack.
